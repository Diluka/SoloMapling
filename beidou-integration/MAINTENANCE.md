# 北斗集成维护说明

本说明面向维护本仓库的开发者，解释版本来源、更新边界和验收要求。具体构建命令见 [构建说明](README.md)；本轮工作状态见 [总跟踪任务 #1](https://github.com/Diluka/SoloMapling/issues/1)。

## 维护边界

本仓库保存一份实际运行的机器人代码。原版 Solo 和插件是更新来源，北斗是固定版本的引擎输入。

| 来源 | 用途 | 更新方式 |
| --- | --- | --- |
| `MadaraGameDev/SoloMapling` | 原版机器人框架与资源 | 拉取后审查增量，保留原版 Git 历史 |
| `zmzeng/solomapling-plugin` | LLM、资源和行为修复等功能来源 | 按功能移植，记录来源提交与必要依赖 |
| `BeiDouMS/BeiDou-Server` | 官方北斗引擎 | 通过 submodule 固定已验证版本 |
| `Diluka/SoloMapling` | 自己的开发与交付仓库 | 提交、推送和本项目 PR 在这里进行 |

上游只拉取，不推送。自己的 `origin` 可以推送；上游 remote 和北斗子模块的推送地址应禁用。GitHub 的 Fork 标记不影响这个维护方式，无需为解除标记重写历史。

插件仓库没有继承原版 Solo 的 Git 祖先关系，因此不能把其整树合并当成普通的原版更新。每批功能记录来源仓库、提交范围、已吸收内容和未迁移部分。原版的 Cosmic 引擎修改需要检查其意图，再决定是否属于北斗适配，不直接覆盖北斗引擎。

## 北斗子模块保持原样

当前基线为官方 `1.12`，提交 `75a86268738ca8845e06ea9d59ec36d15b22c91b`。子模块保存官方源码，不在其中修改源码、POM、资源、配置或添加本地适配类。

构建将需要的输入复制到 `beidou-integration/target/` 等暂存目录，先正常编译北斗，再用 Solo 管理的 AspectJ 规则进行二进制织入。构建完成后检查子模块版本和工作区；固定提交及源码校验不符时停止，不把改变过的子模块当作官方输入。

“北斗源码不改”与“北斗字节码不变”是不同要求。此方案保持官方源码输入不变，最终 JAR 的少量北斗类会被织入新的调用点或能力。兼容层和织入规则仍需要随北斗升级维护。

## 更新流程

1. 检查本仓库和子模块的本地改动，保存当前配置、版本和验证记录。
2. 一次更新一个来源，审查提交与实际差异。北斗优先采用明确的稳定发布版本。
3. 更新相应来源或子模块固定提交；在 Solo 侧解决接口、资源和织入点变化。
4. 执行构建和相关测试。织入目标、签名或匹配次数不符合预期时，修正规则后重新验证。
5. 用一致的数据副本做隔离迁移及运行验证，检查日志、网页、端口和实际机器人人数。
6. 通过后启动实际本地服务，验证正常迁移、角色加载和存档；记录游戏客户端行为的已验证与未验证范围。
7. 将版本、提交、命令、结果和限制附到对应 Issue。证据满足验收项后再关闭任务或合并 PR。

正常 `merge` 保留历史，不使用 rebase 或强制推送来消除同步冲突。补丁能够应用、编译能够通过，并不自动证明交易、存档和游戏行为兼容。

## 数据与运行配置

数据结构和正常业务规则由北斗提供，Solo 的机器人身份、模板角色和生命周期仍需验证。不能仅凭“使用北斗数据库”推导出全部行为兼容，更不能将未验证的结果表述为 100% 兼容。

- 变更前备份本地业务配置和一致的数据库副本。运行中的数据库使用一致性备份；数据库目录仅在数据库停止后归档。
- 迁移先在数据副本、独立 Compose 项目和网络验证，不挂载原始数据目录，不占用正式服务的宿主端口。
- 用户已授权正常迁移、模板角色创建和存档等读写；完成隔离验证后按任务执行，并保留结果。
- 不删除、清空或覆盖真实游戏数据，不用真实部署的 `down --volumes` 清理测试。
- `application.yml`、人口配置和密钥继续在本地文件维护，不打入镜像或 JAR，不提交到仓库或日志。
- 保留北斗入口的数据库预初始化与 Spring 配置读取顺序，避免启动前后读取不同配置。

数据库迁移后，降级 JAR 不一定足以回退。回退前确认旧程序与迁移后数据的兼容性，必要时配套恢复变更前的配置和数据库备份。

## 验收记录

| 层次 | 应记录的证据 |
| --- | --- |
| 源码输入 | 北斗固定提交、子模块干净状态、构建前后校验 |
| 构建 | 命令、依赖版本、输出 JAR 校验值、织入结果 |
| 单元与契约测试 | 实际执行范围、通过/失败数、未覆盖项 |
| 数据兼容 | 备份来源、隔离恢复、迁移结果、角色/背包加载与存档回读 |
| 服务运行 | 北斗版本、WZ/脚本、登录及三个频道、实际机器人人数 |
| 网页与端口 | 登录页渲染、静态资源、浏览器错误及端口连接 |
| 游戏行为 | 聊天、组队、交易、物品与金币一致性，以及客户端玩法结果 |

原版机器人与 LLM 是本轮验收范围。持久伙伴、职业成长和装备赠送需要单独确认数据库和宿主能力，不能将“未引入”写成“已经完成”。

## 许可与源码提供

整合应用继续采用 [AGPL-3.0](../LICENSE)。复用 AGPL 源码后，不能把整个派生应用改标为 MIT。新增集成代码沿用 AGPL-3.0，保留现有文件的版权及许可版本限制；第三方依赖和素材各自的许可仍有效。

将插件来源代码移入本项目时，保留相关文件头，并在提交或功能记录中写明来源仓库与提交。项目级来源见 [NOTICE](../NOTICE)。不要求将修改提交给上游，但分发程序及向远程用户提供修改后的网络服务时，需要按许可证提供实际运行版本的对应源码。

发布时检查：

- 向使用者显著提供免费获取对应源码的方式，并标明运行构建的提交或发布版本。
- 源码包括实际适配、织入规则、构建脚本和准确的北斗子模块版本；提供源码包时包含所需子模块内容。
- 不把 GitHub 默认生成、缺少子模块内容的 ZIP 当成完整的对应源码包。
- 保留 `LICENSE`、`NOTICE` 和依赖所需的声明；不把用户数据、数据库备份或密钥混入源码包。

## 旧方案清理

旧方案在新方案验收后清理。清理前核对未提交工作和可恢复的版本，保存必要备份；清理目标只包括已确认废弃的本地源码、构建入口及本轮测试资源。真实游戏数据、备份和业务配置不属于废弃源码。

远端旧 Fork 的删除应单独核对具体仓库和授权范围，不因切换本地构建路径自动删除远端仓库。当前任务的验收和清理记录见 [维护任务 #5](https://github.com/Diluka/SoloMapling/issues/5)。
