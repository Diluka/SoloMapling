# 基础练级日程

`TrainingScheduleControlModule` 是类型为 `training-schedule` 的控制模块。它在同一角色运行体上组织“训练场狩猎拾取、容量触发、走到商店出售、返回继续”的循环。模块激活后自动开始，循环由模块自己的受管工作持有；创建调用或脚本 Context 结束后继续运行。

首环地图为训练场Ⅰ `104040000`、射手村 `100000000`、集市 `100000100` 与杂货店 `100000102`。目的地、NPC、容量条件和出售规则来自类型配置；门户路线由旅行规划读取真实定义产生。

## 配置与装配

专用 `training_basic` 类型装配旅行、导航、原生动作、战斗、狩猎、拾取、商店、药剂、恢复及本日程。初始人口由人口文件管理，初始化数量0的类型可按需通过现有 `robots.create` 创建。`mcp_test` 保留独立动作调试，日程由专用类型自动运行。

```yaml
training:
  type: training-schedule
  config:
    training_map_id: 104040000
    shop_map_id: 100000102
    shop_npc_id: 1011100
    hunting_style: PATROL
    capacity:
      inventory_types: [ETC]
      minimum_free_slots: 0
    sale:
      allowed_item_ids: [4000000, 4000011, 4000016, 4000017, 4000021]
      retained_item_ids: [4000001]
      retained_quantities: {}
    check_interval_ms: 500
    revive_on_death: true
```

`inventory_types` 指定关注的普通背包；任一类别的实际空位小于等于阈值时触发回店。允许出售的ID、完整保留ID和保留数量消费共享 `SaleRules`，保留优先。模块的空配置默认未选择出售ID；实际类型应明确给出允许清单。数量与最终售价沿原生商店规则。

临时验收类型和近满背包材料维护在未提交的本地人口文件。材料准备、原生掉落生成、真实入包、容量触发及实际出售分别取证。

## 日程阶段

| 阶段 | 调度及完成依据 |
|---|---|
| `STARTING` | 读取实际地图和背包；已有容量条件时先到店处理，否则进入训练场。 |
| `TO_TRAINING` | 从当前地图请求 `travel.plan`，逐段导航及原生门户进入，确认训练场实际场景。 |
| `HUNTING` | 开始本日程持有的狩猎活动，读取真实容量及独立拾取控制摘要。 |
| `TO_SHOP` | 停止本日程启动的狩猎，等待本次交战退出及已观察的精确装备安排真实结束；逐段前往杂货店。 |
| `SELLING` | 导航到实际NPC，打开普通商店，按当前背包生成明确出售清单，关闭后重新观察空位。 |
| `RETURNING` | 确认配置容量条件已解除后按新计划返场，再开始下一次狩猎。 |

同一活动维持一个阶段进度。每次实际过图后重新捕获当前场景；下一段使用当前地图中的实际门户坐标。`FOUND` 只表示拓扑计划，真实移动、原生准入和场景变化由动作结果确认。

完成出售并返场、下一次狩猎成功开始后，才计入 `cycles_completed`。激活时已经满包的首次整理，以及外部先腾出空间后无需出售的返场，不计为一次完整狩猎售物周期。

## 受阻与生命周期

状态为 `IDLE / RUNNING / BLOCKED / STOPPING / FAILED`。没有可售物、出售后仍无所需空间、路线不可达或协作者暂不可用时，保存当前阶段与原因，等待库存、位置、场景、原生资格或提供者代次等相关事实变化再重评。失败调用期间已有实际移动进展时，从新位置重建安排。

`revive_on_death` 默认 `true`。检测实际死亡后，日程先等待自己的狩猎和商店交互退出，再通过 `native.revive` 请求普通复活。回城、HP/MP及事件裁决仍由原生处理；日程观察到实际存活后，按当前地图和容量重新选择阶段，自动返场并继续原运行。设为 `false` 时以 `dead_waiting_external_revive` 等待外部复活。

原生已受理但尚未复活时，日程保持 `BLOCKED` 并记录 `revive_waiting_event` 或实际结果原因，不重放未知副作用。事件后续恢复存活后正常接续；未知结果需核对，不能用改变位置触发再次点击。

拾取、出售或门户执行出现不确定副作用时，当前运行保持明确受阻状态，已确认事实继续保留。拾取未知门禁使用运行启动时的独立基线，首次赶路阶段还没有Cycle时也会生效；周期基线只用于数量汇总。提供者暂不可用时仍保留原精确实例，重新挂载另一实例以 `loot_provider_changed` 停止本次运行，避免旧计数基线套到新实例。核对后可通过模块生命周期重新激活，按当时真实场景与背包建立新的日程。

`start()`、`stop()` 和 `status()` 为具体 Java 方法。`start()` 重复调用返回 `ALREADY_RUNNING`，收尾期间返回 `BUSY`；`stop()` 等本次日程及其下游真实退出后返回，待命时返回 `ALREADY_IDLE`。模块暂停、停用、卸载及根关闭只收尾本日程持有的狩猎活动和商店交互，使用精确活动/交互ID；拾取、恢复和战术控制保持自身生命周期；日程不停止这些兄弟模块。

重新激活读取当前实际起点并自动开始。日程短观察沿角色原lane执行，长循环及等待不占lane。旅行、导航、门户、商店和狩猎继续使用各自提供者的scope/work；停止不会从已撤销的日程授权借权发新动作。

## 可观察事实

`status().toMap()` 提供当前运行及阶段、原因、实际地图与目的地、已完成周期数、当前未完成周期和最近两个完整周期。

每轮只保留配置关注背包的空位/槽位上限、金币与有界物品数量汇总，以及独立的狩猎击杀、`cycle.loot` 周期拾取序号与数量摘要、出售摘要、最多8段实际门户记录。拾取基线在启动本周期狩猎前读取，`indeterminate_sequence` 防止较早的未知结果被后续正常结果覆盖；背包始终以原生事实为准。门户记录分别包含实际出口前位置和入口后位置。物品数量汇总最多16个配置ID，售出记录最多8项；截断通过相应标记表达。状态不保存完整背包、原生对象或无限历史。

验收需将源码测试、隔离两轮实际业务、主分支部署与正式正常循环分别记录。`cycles_completed` 是日程完成计数；击杀、地物、入包、扣物和金币仍以对应原生事实及实际前后态核对。
